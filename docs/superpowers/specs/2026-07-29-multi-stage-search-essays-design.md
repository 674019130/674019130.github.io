# 多阶段搜索双语文章与博客维护设计

日期：2026-07-29

## 目标

本次变更完成三件相关的博客维护工作：

1. 将多阶段搜索系统的技术分享拆成中文、英文两篇独立文章。
2. 在不暴露具体业务实现的前提下，用通用检索概念解释结果如何产生、为什么完整
   多阶段排序集中在第一页、为什么需要两次时效性校准，以及如何判断 Query
   复杂度。
3. 升级兼容的博客依赖，并重新策展首页置顶文章。

本次不修改搜索服务，不发布内部工程文档，也不改动 GitHub Pages 的自动部署流程。

## 双语文章

新增两个独立文件：

- `pages/posts/multi-stage-search-ranking-zh.md`
- `pages/posts/multi-stage-search-ranking-en.md`

中文标题为《当相关性遇见时效性：多阶段搜索排序的工程设计》，英文标题为 *When Relevance Meets Recency: Engineering a Multi-Stage Search Ranking System*。两篇文章分别设置 `lang: zh-CN` 和 `lang: en`，互相提供语言版本链接，而不是在单篇文章中上下拼接翻译。

两篇文章共享论点和图示，但按各自语言独立润色。它们采用以下结构：

1. 搜索排序首先是目标选择，而不是单一分数公式。
2. 相关性优先与时间优先为什么需要两条路径。
3. Query 复杂度为什么是一个策略信号，而不是简单的“越长越复杂”。
4. 词法召回与语义召回如何组成候选集合。
5. 为什么完整的多阶段智能排序通常集中在第一页，后续页如何保持稳定续查。
6. 两阶段时效性如何分别参与候选形成和最终校准，以及只有其中一次会缺少什么。
7. Rerank 为什么必须保留基础排序先验。
8. 时间排序为什么仍需先做相关性门控与自适应截断。
9. 不同 Query 类型与请求选项如何改变召回和排序路径。
10. 拿到一个 Query 后，如何从路径、召回、过滤、打分和重排推断返回结果。
11. 设计边界、常见误区与结论。

文章使用 Mermaid 绘制四张粗粒度流程图：总路由、相关性路径、第一页与后续页
边界、时间路径。相关性图中会将第一次时效性调整、融合、第二次时效性调整和
Rerank 拆成独立节点。分页图解释有限候选窗口与稳定 Cursor 的权衡，不复刻内部
Cursor 数据结构。图中不出现内部服务名、字段名或精确参数。

## 面向博客的问答表达

工程文档中的三个问题会在博客中保留，但抽象层级不同：

- **为什么完整智能排序集中在第一页：** 解释有限候选窗口无法天然形成可跨页
  恢复的全局顺序；每页重新融合和 Rerank 容易引入重复、遗漏与顺序漂移。后续页
  仍按稳定的词法相关性流继续，不描述为“没有排序”。
- **为什么需要两次时效性：** 第一次影响候选能否进入召回窗口，第二次在不同
  召回分数归一化与融合后校准统一候选集合。只保留前者会缺少最终统一校准，只
  保留后者无法找回未进入候选窗口的内容。
- **如何判断复杂 Query：** 将复杂度描述为一个策略分类器，可综合字符体系、
  描述性词项数量和已知实体例外。博客不公布精确词数门槛、判断顺序、实体表或
  特定语言的生产规则，而是解释为什么“短 Query 不一定简单，长 Query 也不一定
  需要最昂贵的路径”。

Query 用例按输入边界、普通与描述性 Query、非拉丁字符与混合字符、已知实体、
词法-only 请求、精确标识或标题、后续分页、时间排序等通用场景分组。示例使用
虚构或领域无关的文本，不映射线上热词、同义词和实体词表。

## 信息公开边界

文章可以公开以下通用概念：

- BM25 与词法匹配；
- ANN 与语义召回；
- 候选融合、时效性先验、Rerank；
- 相关性门控、自适应 cutoff、时间排序；
- 有限候选窗口与稳定分页之间的权衡；
- Query 复杂度分类器的通用设计维度；
- 基于阶段化诊断理解搜索结果的方法。

文章不包含以下内容：

- 公司、产品、服务、索引或供应商名称；
- 内部缩写、接口、请求字段、调试字段和代码路径；
- 词表内容、真实业务 query 或文章样例；
- 召回窗口、阈值、权重、衰减周期和融合公式的具体数值；
- Complex Query 的精确词数门槛、判断顺序和登记实体清单；
- 中英文路由和特殊 Query 类型的内部规则；
- 能够从公开文字反推出线上配置的组合细节。

屏蔽方式以抽象层级为主，不在正文中反复声明“此处省略内部细节”。

## 兼容性与风险

- 首页内容顺序会明显变化，置顶数量由 14 篇收敛为 6 篇；这是预期的策展行为变化。
- 旧文章只取消置顶，不删除、不改正文，也不改变已有链接。
- Valaxy 从 `0.27.0` 升级到 `0.28.11` 包含构建引擎和 Node.js 最低版本变化，因此必须验证静态构建、Mermaid、搜索、文章列表和 SSG 路由。
- 两篇文章内容相近，但通过独立语言标记、独立摘要和互链降低读者误解；首页相邻展示是有意设计。
- 博客对 Complex Query 使用概念化表达，不能被误读为线上规则的完整复刻；精确
  条件只存在于搜索代码库的工程文档中。
- GitHub Actions 仍在 `main` push 后自动构建并部署。本分支在本地验证通过后先提交供复核，不直接触发线上发布。

## 验证与完成标准

实施完成后执行：

1. `pnpm install --frozen-lockfile`，确认 pnpm 锁文件可复现。
2. `pnpm exec tsc --noEmit`，执行现有 TypeScript 类型检查并记录任何存量错误。
3. `pnpm build`，验证 Valaxy SSG 构建。
4. 本地预览首页、两篇新文章和 Stats Card 直链。
5. 检查八张 Mermaid 图、目录、语言标记、互链、置顶顺序和移动端布局。
6. 扫描文章中的内部标识、精确参数和占位符。
7. `git diff --check`，检查格式问题。

成功标准是：两篇文章均可独立阅读，能回答分页、两阶段时效性和复杂度分类三个
问题且无内部实现泄露；首页仅展示六篇有序置顶文章；Stats Card 从首页和归档
隐藏；依赖安装与生产构建成功；现有文章路由无回归。
